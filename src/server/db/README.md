# قاعدة البيانات — دليل التشغيل

**الحالة الآن:** لم يُشغَّل أي ترحيل على أي قاعدة بيانات. التطبيق يعمل على
بيانات البذرة المحلية (`DATA_SOURCE` فارغ). كل ما في هذا المجلد **جاهز
للتفعيل، غير مُتحقَّق منه** — لم يُختبر مقابل قاعدة بيانات حقيقية بعد.

---

## ترتيب تشغيل الترحيلات

الترتيب **إلزامي** — كل ملف يعتمد على ما قبله عبر المفاتيح الأجنبية.

| # | الملف | ينشئ |
|---|---|---|
| 0 | `0000_base_customers_vehicles.sql` | العملاء، المركبات |
| 1 | `0001_customers_billing_fields.sql` | حقول الفوترة على العملاء |
| 2 | `0002_invoices.sql` | الفواتير، البنود، سجل التدقيق |
| 3 | `0003_daily_closing.sql` | تقفيل اليومية، القيود، سجل التدقيق |
| 4 | `0004_work_orders.sql` | أوامر التشغيل + بنود/قطع/خط زمني |
| 5 | `0005_appointments_estimates.sql` | المواعيد، التقديرات + بنودها |
| 6 | `0006_inventory_purchasing.sql` | قطع الغيار، أوامر الشراء + بنودها |
| 7 | `0007_accounting_hr_marketing.sql` | القيود، الموظفون، الحملات، التقارير |
| 8 | `0008_enable_rls_on_legacy_tables.sql` | **إصلاح أمني** — RLS على جداول 0002 و0003 |
| 9 | `0009_auth_profiles_and_rls.sql` | ملفات المستخدمين، مصفوفة الصلاحيات، **كل سياسات RLS** |

الملفان 8 و9 ليسا اختياريين ولا مؤجَّلين. جداول 0002 و0003 تُنشأ بلا RLS،
ومفتاح `anon` في Supabase علني بالتصميم — أي جدول بلا RLS مقروء ومكتوب للعالم.
والملف 9 هو ما يمنح الوصول أصلًا: بدونه RLS مفعّل بلا سياسات = **لا أحد يقرأ
شيئًا** (ما عدا `service_role`).

**تحقّق مؤتمت أُجري على الملفات:** ٢٤ جدولاً، كلها بـ RLS مفعّل، وكلها لها
سياسة واحدة على الأقل. لا جدول متروك.

### كيف تشغّلها

لوحة Supabase ← SQL Editor ← الصق محتوى كل ملف بالترتيب وشغّله.

### تحقّق إلزامي بعد الانتهاء

```sql
select tablename
from pg_tables
where schemaname = 'public' and rowsecurity = false;
```

**يجب أن يعيد صفر صفوف.** أي جدول يظهر هنا مكشوف للعالم.

## تفعيل الاتصال

1. `cp .env.example .env.local`
2. املأ القيم من: Project Settings ← API
3. `DATA_SOURCE=supabase` في `.env.local`
4. أعد تشغيل خادم التطوير

المفاتيح ناقصة مع `DATA_SOURCE=supabase` = **فشل فوري عند الإقلاع**، لا سقوط
صامت إلى بيانات البذرة. نظام محاسبي يعرض أرقام بذرة وهو يظن نفسه متصلًا
بقاعدة البيانات أسوأ من نظام يرفض الإقلاع.

للرجوع لبيانات البذرة: احذف `DATA_SOURCE` أو اتركه فارغًا.

## ما **لم** يُنجَز بعد

- [ ] **نقل بيانات البذرة إلى قاعدة البيانات** — الترحيلات تنشئ جداول فارغة.
      لا سكربت seed بعد.
- [ ] **التحقق من المحوّل مقابل قاعدة حقيقية.** أول تشغيل يجب أن يقارن مخرجات
      `supabaseRepositories` ببيانات البذرة صفًا بصف، خصوصًا المبالغ: أعمدة
      `numeric` تعود من Postgres **نصًا لا رقمًا**، والمحوّل يمرّرها عبر `num()`
      التي ترفض `NaN` — لكن هذا لم يُختبر على بيانات حقيقية.
- [ ] **الكتابة.** المحوّل للقراءة فقط (`findAll` / `findById`). الإنشاء
      والتعديل ما زالا في `localStorage` عبر `modules/*/client-store.ts`،
      ويحتاجان Server Actions.
- [ ] **⚠️ أهم بند: القراءات ما زالت تمرّ بمفتاح `service_role`.**
      `src/server/repositories/supabase/` يستخدم `getSupabaseAdmin()` الذي
      **يتجاوز RLS بالكامل**. سياسات المرحلة د مكتوبة لكنها لا تُطبَّق على
      القراءات فعليًا حتى يُحوَّل المحوّل إلى `getSupabaseServerClient()`
      (العميل الذي يحمل جلسة المستخدم). حتى ذلك الحين الحماية من `proxy.ts`
      و`getSession()` فقط — وهما قابلان للتجاوز نظريًا.
- [ ] **إنشاء المستخدمين وصفوف `profiles`** — لا تسجيل ذاتي (متعمَّد).

## قرار تصميمي: المعرّفات نصية

الجداول الجديدة تستخدم `text` كمفتاح أساسي لا `uuid`، لأن التطبيق يستخدم
معرّفات مثل `customer-001` وأنواع TypeScript موسومة بها
(`CustomerId = \`customer-${string}\``). هذا يحفظ التوافق ويسمح باستيراد
البذرة بلا إعادة ترقيم. الاستثناء: `invoices` و`daily_closings` تستخدمان
`uuid` لأنهما كُتبتا في ترحيلات سابقة — وهو مناسب لهما (متطلب فاتورة يفرض
UUID لكل مستند).
